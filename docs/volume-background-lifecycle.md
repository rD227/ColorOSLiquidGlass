# 音量背景冻结：生命周期检查

现象：音量可以调整，玻璃背景画面不更新；重启 Launcher/SystemUI 后恢复。
当时手机安装的 APK 不包含新加的通知 0 Hz 状态，不能把该现象归因于通知 0 Hz。
用户怀疑与切换输出设备有关，但目前没有复现具体的切换顺序。

## 确定的问题与修改

### 关闭后遗留的安装回调

`VolumePanelGlass.schedule()` 原来在当前时刻及 32、120、280、520 ms 后安装玻璃，
`release()` 没有取消这些回调。关闭/重建发生在这段时间内时，旧回调仍可以执行
`apply()`，重新绑定采样；旧面板的全局安装清理也可能干扰后续面板。

现在以请求安装的 dialog 为所有者记录回调。同一 dialog 的新请求替换旧请求，关闭时
移除尚未执行的任务，最后一次执行后释放记录。保留原来的五个安装时机。
这是确定的关闭时序缺陷，不等于已经证明切换设备会触发本次冻结。

### 连接未就绪时的 OPEN 状态

`openSessionIfNeeded()` 原来调用无返回值的 `signalOpen()`，仅以 epoch 是否变化判断
成功。握手版本不匹配、缺少 FD 等拒绝路径返回时不一定改变 epoch，因此不能据此
证明已取得 LIVE 引用。连接尚未就绪时还可能在 UI 线程进行同步握手。

新增 `trySignalOpen()` 返回是否实际取得引用，保留原有 `signalOpen()` API。
宿主只在后台预热完成且 OPEN 成功后记录已打开；预热未完成时由后续正常绘制继续处理。
没有添加超时重试循环或失败后伪造画面。

## 验证范围

- Release 构建、本地配置/采样节流回归、设备探针编译通过。
- `VolumeLifecycleProbe` 已在手机上的独立 app_process 中通过：重复安装合并、关闭
  取消、替换面板、最后回调释放、未连接时保持关闭、已连接时只取得一次引用、关闭释放引用。
- IPC 测试使用测试进程自己的共享内存，不连接桌面的真实生产者；没有安装 APK、重启
  SystemUI、修改音量或切换音频输出设备。

仍需在真实输出设备切换时确认 OEM 的显示/关闭回调顺序。不能把“重启后恢复”单独当作
某一个根因的证据；共享内存生产者、View 重建和异步截图也都可能留下旧状态。
本轮调用 agy 做独立 IPC 审查，但三分钟超时，仅返回读取进度，没有完整审查结论。

## 补充复核：跨面板、跨代际与 STOP/LIVE

异步完成晚于关闭、旧面板晚于新面板收到 dismiss 都是正常可达的时序，不能要求 OEM
回调替我们保证先后关系。原先用一个全局安装集合、无代际引用计数和跨线程采样状态
表示这些对象，才是内部所有权不完整的问题。

### 面板所有权

安装记录现在是 View → 弱引用 dialog。清理消失的 View 以及 release 都只处理该 dialog
拥有的记录；若 View 已交给新 dialog，旧 dialog 不再有权卸载它。逐个卸载宿主本身
已经关闭对应的采样，因此删除 release 中无条件的 stopVolumeSessions 调用。
